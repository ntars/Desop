## 一、项目名称与定位

> **仓库描述 / Description**：`Desop —— Windows 端桌面美化套装：把 macOS 桌面观感复刻到 Windows，提供 dock 栏、顶部栏、桌面小组件与灵动岛（规划中） | A Windows desktop beautification suite: macOS-style dock, menu bar, widgets and dynamic island. Planned, no code yet.`
>
> **话题标签 / Topics**（20 个，仅英文）：`beautification`, `desktop-customization`, `desktop-widgets`, `dock`, `dynamic-island`, `macos-style`, `menubar`, `planned`, `theme`, `ui`, `user-mode`, `windows`, `windows-10`, `windows-11`, `desktop-environment`, `taskbar`, `wallpaper`, `theming`, `windows-desktop`, `concept`


**名称**：Desop。取 Desktop 的 Des 与 op（operation / 操作层）——桌面操作层。

**一句话定位**：在 Windows 上重建一套 macOS 式的桌面交互层，让「换系统」不再等于「换习惯」。

**定位的三条边界**：

1. **它是桌面层，不是系统层**。所有元素都跑在用户态，不改系统文件、不替换 shell、不需要禁用系统更新。卸载即还原。
2. **它追求观感与手感，不追求像素级复刻**。macOS 的圆角、毛玻璃、动效曲线可以学，但 Windows 的窗口管理、任务栏行为是系统契约，不硬改。
3. **它是一套可拆的组件，不是一个整包**。dock、顶部栏、小组件、灵动岛各自独立，用户可以只开其中一两个。

**与 macOS 的关系**：本项目参照 macOS 的桌面交互设计，不复用其任何代码、素材或字体。所有视觉元素为独立实现。

## 二、项目简介

### 2.1 背景

从 macOS 转到 Windows 的人，最先不适应的往往不是功能缺失，而是**交互习惯的断裂**：没有顶部全局菜单、没有 dock 的图标放大与弹跳、没有随手的桌面小组件、通知只有右下角一个气泡。

现有方案通常两个极端：要么是重度美化包，改注册表、换 shell、动系统文件，出问题难恢复；要么是单个小工具，只管 dock 或只管小组件，风格各自为政，凑在一起反而更乱。

### 2.2 要解决的问题

1. **观感割裂**。四个元素分别来自不同工具时，圆角半径、阴影、动效时长、字体全不一致，看起来像四个软件拼在一起。
2. **风险不可控**。改系统文件的方案一旦出问题，恢复成本高，普通用户不敢尝试。
3. **性能负担**。毛玻璃与实时模糊如果实现粗糙，会让整机掉帧，美化变成负担。

### 2.3 核心思路

统一一套设计令牌，四个组件共享：

| 令牌 | 作用 |
|---|---|
| 圆角与间距 | 所有组件用同一套数值，不各写一份 |
| 阴影与材质 | 毛玻璃的模糊半径、透明度、边界光统一 |
| 动效曲线 | 时长与缓动函数统一，避免「有的弹有的滑」 |
| 字体与字号 | 跟随系统但统一档位 |

四个组件各自独立进程或模块，共享令牌，互不依赖——关掉一个不影响其余。

### 2.4 适用场景

- 从 macOS 转到 Windows、想保留原有操作习惯的用户；
- 喜欢整洁桌面、希望有 dock 与小组件但不想装重型美化包的用户；
- 需要长期稳定运行、不能接受「美化导致系统异常」的用户。

### 2.5 非目标

- 不改系统文件、不替换 `explorer.exe`、不修改受保护的系统设置；
- 不做主题商店、不做壁纸分发；
- 不做性能监控、硬件信息类小组件的深度数据采集（只读系统公开接口）；
- 不承诺与 macOS 行为完全一致——系统契约不同的地方以 Windows 为准。

## 三、核心功能

**本章全部为规划中，四个组件均未实现。**

### 3.1 Dock 栏

| 能力 | 说明 | 状态 |
|---|---|---|
| 图标放大 | 指针靠近时相邻图标按距离衰减放大，模仿 macOS 的磁吸效果 | 规划中 |
| 运行指示 | 已运行应用下方显示指示点 | 规划中 |
| 弹跳反馈 | 启动中弹跳，可关闭 | 规划中 |
| 自动隐藏 | 贴边隐藏，触发区宽度可调 | 规划中 |
| 位置 | 底部 / 左侧 / 右侧 | 规划中 |
| 多显示器 | 每个显示器独立 dock 或仅主屏 | 规划中 |

### 3.2 顶部栏

| 能力 | 说明 | 状态 |
|---|---|---|
| 全局菜单 | 显示当前前台窗口的菜单项（受 Windows 应用支持程度限制） | 规划中 |
| 状态区 | 时间、日期、电量、网络、音量 | 规划中 |
| 托盘收纳 | 把系统托盘图标收进顶部栏，减少右下角拥挤 | 规划中 |
| 自动隐藏 | 全屏应用时自动隐藏 | 规划中 |

**已知限制**：Windows 应用不强制暴露菜单结构，全局菜单只能对支持标准菜单 API 的应用生效，其余显示为空。这一条在排期阶段就要说清，不做「全部应用都能用」的承诺。

### 3.3 桌面小组件

| 能力 | 说明 | 状态 |
|---|---|---|
| 时钟日历 | 大号时钟、月历、日程摘要 | 规划中 |
| 系统状态 | CPU / 内存 / 磁盘 / 网络速率（只读公开接口） | 规划中 |
| 便签 | 本地纯文本便签，不联网 | 规划中 |
| 天气 | 需用户自行填入数据源，默认不联网 | 规划中 |
| 布局 | 自由拖拽、吸附对齐、网格吸附可关 | 规划中 |

### 3.4 灵动岛

| 能力 | 说明 | 状态 |
|---|---|---|
| 常驻形态 | 屏幕顶部居中的胶囊，收起时极小 | 规划中 |
| 展开动效 | 点击或事件触发时展开，带弹性曲线 | 规划中 |
| 事件接入 | 音乐播放、下载进度、通知摘要、计时器 | 规划中 |
| 第三方接入 | 提供本地接口，允许其他程序推送状态 | 规划中 |

**说明**：灵动岛在 macOS 上是硬件与系统的结合产物，Windows 上没有对应机制，本项目的实现是**纯软件模拟**——通过读取系统媒体会话、下载进度等公开信息来驱动。这一点必须写明，不能让人误以为是系统级能力。

### 3.5 明确不做

- 不做壁纸引擎与动态壁纸；
- 不做窗口特效（如圆角、透明）的强制注入；
- 不做系统主题色替换；
- 不做开机动画修改。

## 四、核心特性

**本章为设计意图，尚未实现，故不提供可复现证据。** 待首个可运行版本发布后，此处将逐条补齐「实现方式」与「证据」。

### 亮点一：零系统改动，卸载即还原

- **亮点名称**：纯用户态实现。
- **价值**：解决「美化包出问题后系统起不来」的恐惧，这是普通用户不敢尝试美化工具的首要原因。
- **实现方式（规划）**：不写系统目录、不替换 shell、不注入 explorer 进程。所有元素是独立进程的窗口，通过公开 API 与系统交互。
- **差异化**：多数重度美化包要求关闭系统更新、替换系统文件，一旦失败恢复成本极高。
- **证据**：待实现后提供。当前可核对的是本项目已把「零系统改动」写入第十三章安全原则与第十四章兼容性边界。

### 亮点二：一套设计令牌，四个组件风格一致

- **亮点名称**：统一令牌层。
- **价值**：解决「四个工具拼在一起，圆角阴影动效全不一样」的问题。
- **实现方式（规划）**：圆角、间距、阴影、模糊半径、动效时长与缓动曲线集中定义，组件只读不写。
- **差异化**：多数方案由不同作者分别开发，风格天然不一致。
- **证据**：待实现后提供。

### 亮点三：性能预算作为发布门槛

- **亮点名称**：三条硬指标。
- **价值**：解决「装了美化工具整机变卡」的问题——这是美化工具被卸载的第二大原因。
- **实现方式（规划）**：空闲 CPU < 1%、空闲内存 < 150 MB、dock 放大动画 ≥ 55 fps。达不到不发布。
- **差异化**：多数工具把性能当「后续优化」，本项目把它当准入门槛。
- **证据**：待实现后提供。

### 亮点四：组件可选，不做捆绑

- **亮点名称**：按需启用。
- **价值**：解决「我只想要 dock，却被塞了四个东西」的问题。
- **实现方式（规划）**：四个组件独立，可单独安装与关闭，关闭后不驻留进程。
- **差异化**：整包式美化工具常把全部组件绑在一起。
- **证据**：待实现后提供。

### 亮点五：复用系统能力优先，不硬造

- **亮点名称**：系统模糊优先于自绘模糊。
- **价值**：解决「自绘毛玻璃导致耗电与掉帧」的问题。
- **实现方式（规划）**：优先调用 DWM / 亚克力等系统提供的模糊效果，自绘只在系统不支持时兜底。
- **差异化**：自绘模糊在低端机上代价极高，且与系统合成器争抢资源。
- **证据**：待实现后提供。

## 五、设计细节与工程取舍

**本章为设计约定，实现时须遵守。**

### 5.1 灵动岛的事件来源要诚实

灵动岛不是系统能力，因此必须明确每个事件的来源：

| 事件 | 来源 | 局限 |
|---|---|---|
| 音乐播放 | 系统媒体会话（SMTC） | 部分播放器不上报 |
| 下载进度 | 应用主动推送（本地接口） | 需应用配合 |
| 通知摘要 | 系统通知监听 | 需用户授权 |
| 计时器 | 本程序内部 | 仅本程序 |

**不做的事**：不假装能拿到所有应用的状态。拿不到就不显示，而不是编一个。

### 5.2 全屏应用的避让

- 全屏应用运行时，顶部栏与 dock 自动隐藏；
- 检测方式优先用系统提供的全屏状态，而非窗口尺寸猜测；
- 检测不到时宁可保留，不做激进隐藏——误隐藏比多显示更烦人。

### 5.3 DPI 与多显示器的边界

- 每个显示器独立计算缩放比例，不共用一套坐标；
- 跨屏拖动时按目标屏的 DPI 重算，不做插值动画——插值会让图标在跨屏瞬间变形；
- 混合 DPI（如 4K 主屏 + 1080p 副屏）是必须测试的场景。

### 5.4 毛玻璃的降级链

```
系统亚克力（Win11） → 系统模糊（Win10） → 半透明纯色 → 不透明
```

每一级都要能自动降级，且降级后视觉仍成立。不允许出现「系统不支持就变成一块黑」。

### 5.5 图标放大的性能边界

- 只对可见区域的图标计算放大，屏幕外的跳过；
- 放大范围有上限（默认指针左右各 3 个图标）；
- 走合成层变换，不触发布局重排。

### 5.6 卸载的完整性

卸载后必须还原：

1. 开机自启项；
2. 注册表启动项；
3. 桌面快捷方式；
4. 用户数据目录（询问是否保留配置）。

**这一条是验收项，不是可选项。**

## 十五、已知问题与限制

### 15.1 当前阶段的事实

1. **没有代码**。仓库内只有文档与许可证。
2. **没有时间表**。排期阶段不承诺发布日期。
3. **技术路线未定**。第六章的构想可能被验证结果推翻。

### 15.2 已识别的设计限制

| 限制 | 原因 | 是否可解 |
|---|---|---|
| 全局菜单覆盖面有限 | Windows 应用不强制暴露菜单结构 | 不可解，只能尽力 |
| 灵动岛是软件模拟 | Windows 无对应系统机制 | 不可解，事件来源受限 |
| 部分模糊效果依赖系统版本 | Win10 与 Win11 能力不同 | 通过降级链缓解 |
| 可能被安全软件误判 | 涉及系统级钩子的功能 | 需提前验证，必要时放弃该功能 |

### 15.3 排期阶段必须先回答的问题

答不上就不进入开发：

| 问题 | 为什么关键 |
|---|---|
| 各 Windows 版本的模糊效果可用性 | 决定毛玻璃是否需要自绘兜底 |
| 全局菜单在常见应用上的覆盖率 | 决定这个功能是否值得做 |
| 多显示器与 DPI 缩放的边界情况 | 决定布局计算复杂度 |
| 是否会被反作弊 / 安全软件误判 | 涉及系统级钩子的功能必须提前确认 |
| 卸载后能否完全还原 | 决定用户是否敢装 |

## 十七、后续路线图

按依赖关系排序，前一项是后一项的前提。**全部未开始。**

1. **技术验证**：回答 15.3 节的五个问题，特别是「卸载能否完全还原」与「是否被安全软件误判」。
2. **设计令牌层**：先把圆角、阴影、动效曲线定下来，再谈组件——否则四个组件会各长一套。
3. **Dock 栏**：单独打通，验证性能预算能否达到。
4. **桌面小组件**：验证拖拽与吸附的手感。
5. **顶部栏**：先做状态区与托盘收纳，全局菜单视覆盖率决定是否做。
6. **灵动岛**：最后做，因为它依赖前几个组件已经稳定的动效基础。

可以做的事：
